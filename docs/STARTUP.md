# 起動の修正（2026-09-09）

デスクトップの「Cutton」を開くか、Sitesの「Cuttonを起動」を押します。編集エンジンが停止していれば起動し、準備を確認した後に既定のブラウザでプロジェクト選択画面を開きます。起動済みならエンジンを再利用します。Sitesの「起動済みのCuttonを開く」は今のブラウザでPC版へ移動します。

## 修正した原因

Sitesからlocalhostへの通常のリンク移動に付く `Sec-Fetch-Site: cross-site` が、API用の保護で拒否されていました。ループバック接続・正しいHostのまま、GETによる `/` と `/index.html` のトップレベル文書移動だけを許可します。返すのは公開可能なアプリ画面のHTMLで、プロジェクト情報ではありません。API・素材・ダウンロード・埋め込み・POSTへの制限は維持しています。

Sitesの初期表示ではPCへの自動接続を行わず、起動操作を表示します。そのため初回のローカルネットワーク許可や接続失敗で全面エラーになる流れを避けます。「別の開き方 → この画面で接続する」を選んだ場合は従来のSites内編集も使えますが、そのブラウザのローカルネットワーク許可が必要です。接続待ちは自動再試行し、成功後は通常間隔の更新へ戻ります。

## PCの起動登録

`scripts/install-launcher.ps1` で、このWindowsユーザー専用の `cutton://` とデスクトップショートカットを登録しました。起動先はこのチェックアウトの `scripts/launch.vbs` に固定し、URL引数を渡しません。URLから任意のコマンド・ファイル・プロジェクトを指定することはできません。既存の別アプリ登録がある場合は上書きしません。

起動時は黒いターミナルを表示せず、ポートごとの排他処理で二重起動を抑え、Cuttonのヘルス応答を確認してから画面を開きます。他のアプリが同じポートを使用している場合は終了・乗っ取りをせず、その旨を表示します。起動失敗の詳細は `output/server-error.log` に残します。

Webブラウザによっては初回に外部アプリを開く確認が出ます。ブラウザが独自URLを扱えない場合はデスクトップショートカットを使用します。この登録はこのPCに限られ、他PCではセットアップが必要です。PCのログイン時に常駐を強制する設定は追加していません。

## 検証

Sites由来の文書移動がHTMLを返し、API・素材・iframe・POST・非ループバックHostが引き続き拒否されることをHTTPテストで確認しました。ヘルス確認付きの停止状態からの起動・起動済みエンジンの再利用をPC上で確認しました。エラーが出ていたタブを更新後、WebMCP経由でプロジェクト選択待ち・保存済み3プロジェクトの一覧取得・不正入力拒否を確認しました。カスタムURLの外部アプリ確認画面の挙動はブラウザ依存です。
